# Метрики и события

| Параметр | Значение |
|---|---|
| Версия | 1.0 |
| Источник | `Авито_ТЗ.docx` §6 (снимок: [`tz/avito-tz.md`](tz/avito-tz.md)) |
| Владелец схемы событий | backend (`AnalyticsEvent`) |
| Кто эмитит | только backend; frontend событий аналитики не пишет |

## 0. Единица анализа и окно наблюдения

Единица анализа — **одна задача подачи запроса** (`task_instance_id`), а не
сообщение чата. Повторы одной операции не увеличивают число задач или успехов.
Окно для пилота — **24 часа с начала задачи** (`task_started → +24h`); метрики
считаются только по задачам с закрытым окном, доля незавершённых показывается
рядом.

## 1. Метрики (§6 ТЗ)

| Метрика | Определение | Источник / ответственность |
|---|---|---|
| **Основная:** доля корректно поданных запросов без рутинной помощи | число начатых задач, где в окне создана и проверена корректная заявка без помощи наставника при подготовке / все подходящие начатые задачи с закрытым окном | backend: результат сервиса; Product: проверка корректности |
| Время до корректной подачи | время от старта задачи до подтверждённого сохранения корректной заявки; медиана, число наблюдений и доля незавершённых рядом | события backend; Product/DS: расчёт |
| Рутинная нагрузка наставника | минуты на повторяющиеся организационные объяснения и исправление ошибочных заявок на стажёра за сопоставимый период | короткий дневник/разметка наставника; не только клики в чате |
| Повторное обращение по той же задаче | доля завершённых задач, потребовавших исправления или повторной помощи в выбранном окне наблюдения | связанные события + опрос/дневник; зрелые окна |
| Качество ответа (RAG Faithfulness) | доля проверенных ответов, где утверждения подтверждаются доступными источниками и соответствуют контексту роли/команды | размеченный eval-набор, проверка Product + ML |
| Корректность действия (Tool Accuracy) | доля проверок, где выбран нужный инструмент, параметры и права верны, а результат правильно отображён | eval и интеграционные тесты |
| Инженерные ограничения | покрытие строк прикладного кода >80%; ориентир локального UI <1 с; отдельно задержки модели/сервиса и ошибки | воспроизводимые отчёты тестов и измерения |

Бизнес-результат пилота: снижение минут рутинной помощи наставника на стажёра за
сопоставимый период без ухудшения успешности адаптации. Основная операционная
метрика проверяет выбранный сценарий, но сама по себе ещё не доказывает экономию
времени наставника.

## 2. Tracking plan: 9 событий (§6 ТЗ)

| Событие | Где фиксируется | Условие |
|---|---|---|
| `task_started` | backend | создан экземпляр выбранной задачи |
| `answer_delivered` | backend | ответ доставлен; есть метаданные источников без закрытого содержимого |
| `action_proposed` | backend | создан валидный черновик действия |
| `action_confirmed` | backend | получено подтверждение пользователя |
| `action_succeeded` | backend | получен и сохранён подтверждённый результат сервиса |
| `action_failed` | backend | подтверждена неудача операции |
| `action_status_unknown` | backend | нужна сверка результата после неопределённого исхода |
| `handoff_requested` | backend | пользователь запросил помощь человека |
| `task_feedback_submitted` | backend | получена оценка решения задачи |

Момент отправки в сценарии и дополнительные поля — в
[`../specs/access-request.md`](../specs/access-request.md) §14.

## 3. Общие поля события

Обязательны для всех девяти событий:

| Поле | Тип | Смысл |
|---|---|---|
| `event_id` | string (UUID) | уникальность записи, идемпотентность доставки |
| `event` | enum из §2 | имя события |
| `occurred_at` | string (RFC 3339, UTC) | время события |
| `actor_ref` | string | синтетический/псевдонимный идентификатор пользователя (`user_id` сида) |
| `task_instance_id` | string | единица анализа, `tsk_901` в MVP |
| `scenario_id` | string | `scn_team_space_access` |
| `scenario_version` | string | версия сценария |
| `operation_id` | string \| null | при наличии операции |
| `outcome` | enum | `ok` \| `denied` \| `error` \| `unknown` |
| `error_category` | string \| null | `rbac` \| `validation` \| `upstream_timeout` \| `upstream_error` \| `internal` |
| `duration_ms` | integer \| null | длительность операции/ответа |
| `model_version` | string \| null | версия LLM-провайдера/промпта |
| `test_mode` | boolean | признак тестового/демо-режима |

Запрещено записывать: ключи и токены, полный текст сообщений пользователя,
содержимое закрытых документов (`doc_03`), персональные данные за пределами
синтетического сида.

## 4. План проверки

- Контракт события (`AnalyticsEvent`) проверяется тестом схемы: обязательные поля,
  enum-значения, отсутствие запрещённых полей.
- Сценарные тесты AC-01…AC-06 проверяют последовательность событий: успех — не
  более одного `action_succeeded` на `task_instance_id`; таймаут — `action_status_unknown`
  без `action_succeeded`; отказ RBAC — ни одного `action_confirmed`.
- Корректность и полнота ответов (RAG Faithfulness, Tool Accuracy) считаются на
  размеченном eval-наборе из [`../evals/`](../evals), а не по кликам в чате.
- Отчёты покрытия прикладываются по каждому модулю (backend, LLM, frontend)
  отдельно, без усреднения процентов (см. [`PRD.md`](PRD.md) §9).

## 5. Разрывы с планом §6 ТЗ

| Разрыв | Причина | Решение |
|---|---|---|
| `task_feedback_submitted` не отправляется в MVP | §4 ТЗ не содержит элемента оценки задачи, а §6 требует событие | событие описано и зарезервировано; UI-оценка — открытый вопрос [`PRD.md`](PRD.md) §12 |
| Метрики, требующие дневника наставника, не выводятся из событий | рутинную нагрузку нельзя измерить кликами | сбор вне системы (дневник/разметка), Product фиксирует вручную |
| Окно 24 часа считается офлайн | в MVP нет планировщика | расчёт по выгрузке событий, не в реальном времени |

Отдельно: прежние события `access_request_*` и `agent_tool_failed` из первой
версии этого документа не соответствуют §6 ТЗ и удалены; источником истины
является таблица §2.
