## 0. Единица анализа и окно наблюдения

Единица анализа — **одна задача подачи запроса** (`task_instance_id`), а не
сообщение чата. Повторы одной операции не увеличивают число задач или успехов.
Окно для пилота — **24 часа с начала задачи** (`task_started → +24h`); метрики
считаются только по задачам с закрытым окном, доля незавершённых показывается
рядом.

## 1. Метрики (§6 ТЗ)

| Метрика | Определение | Источник / ответственность |
|---|---|---|
| **Основная:** доля корректно поданных запросов без рутинной помощи | число начатых задач, где в окне создана и проверена корректная заявка без помощи наставника при подготовке / все подходящие начатые задачи с закрытым окном | backend: результат сервиса; Product: проверка корректности |
| Время до корректной подачи | время от старта задачи до подтверждённого сохранения корректной заявки; медиана, число наблюдений и доля незавершённых рядом | события backend; Product/DS: расчёт |
| Рутинная нагрузка наставника | минуты на повторяющиеся организационные объяснения и исправление ошибочных заявок на стажёра за сопоставимый период | короткий дневник/разметка наставника; не только клики в чате |
| Повторное обращение по той же задаче | доля завершённых задач, потребовавших исправления или повторной помощи в выбранном окне наблюдения | связанные события + опрос/дневник; зрелые окна |
| Качество ответа (RAG Faithfulness) | доля проверенных ответов, где утверждения подтверждаются доступными источниками и соответствуют контексту роли/команды | размеченный eval-набор, проверка Product + ML |
| Корректность действия (Tool Accuracy) | доля проверок, где выбран нужный инструмент, параметры и права верны, а результат правильно отображён | eval и интеграционные тесты |
| Инженерные ограничения | покрытие строк прикладного кода >80%; ориентир локального UI <1 с; отдельно задержки модели/сервиса и ошибки | воспроизводимые отчёты тестов и измерения |

Бизнес-результат пилота: снижение минут рутинной помощи наставника на стажёра за
сопоставимый период без ухудшения успешности адаптации. Основная операционная
метрика проверяет выбранный сценарий, но сама по себе ещё не доказывает экономию
времени наставника.

- Синтетические сценарии из `evals/tasks/` прогоняются на staging перед релизом.
- События сверяются с ожидаемыми в `evals/expected/` (наличие, обязательные поля).
- Дашборд Grafana (в планах, см. `infra/README.md`): заявки по статусам,
  p95 времени ответа API, доля ошибок инструментов.
- Продуктовые события дублируются в Clickstream для сквозной воронки.

## 4. Качество AI (ML-сервис)

Определения и протокол — [`specs/ml-agent.md`](../specs/ml-agent.md#5-оценка-качества), автоматический прогон —
`python ml/scripts/run_evals.py`, сводка — [`evals/reports/latest.md`](../evals/reports/latest.md).

| Метрика | Определение | Порог / текущее | Источник |
|---|---|---|---|
| Tool Accuracy | доля ходов eval, где верно решено, вызывать ли `propose_access_request`, с верными аргументами и правами | ≥ 95 % / 100 % | `evals/tasks/dialogs.jsonl` |
| RAG Faithfulness | доля проверенных ответов, утверждения которых подтверждены доступными источниками и контекстом роли/команды | автопрокси 86.9 %; ручная разметка в пилоте | eval + разметка Product+ML |
| Отказ «нет данных» (AC-05) | precision / recall ответа `no_data` на вопросы вне базы | recall ≥ 95 % / 100 % | eval |
| Утечки | ответы с содержимым или источником закрытых для роли документов | 0 / 0 | eval, инвариант каждого хода |
| Ложный успех | ответы «доступ выдан» при тикете не в `provisioned` | 0 / 0 | eval, инвариант каждого хода |
| Recall@3 поиска | доля запросов, где релевантный документ в топ-3 (после ACL) | 95.3 % | `evals/tasks/retrieval.jsonl` |
| Латентность ML | p50 / p95 времени хода агента в локальном режиме | 2.2 / 3.7 мс | `meta.latency_ms` |
| Доля fallback | доля ходов с `meta.mode = local_fallback` (сбой/таймаут LLM) | мониторинг | `meta.mode` в `answer_delivered` |

ML-сервис возвращает в каждом ответе поле `analytics` (`answer_delivered` / `action_proposed`) с метаданными —
интент, тип ответа, doc_id источников, режим, версия сценария — без текста диалога. Backend добавляет общие
поля событий (event_id, время, псевдонимный user_id, task_instance_id) и публикует событие.
