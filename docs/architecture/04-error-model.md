# Единая модель ошибок

## 1. Формат

Ошибки возвращаются JSON-объектом (§10.3 ТЗ задаёт именно такую форму — плоскую,
без обёрток):

```json
{
  "error_code": "UPSTREAM_TIMEOUT",
  "message": "Сервис доступов не ответил вовремя. Заявка могла быть создана. Не создавайте новую заявку -нажмите «Проверить статус операции».",
  "operation_id": "op_5512",
  "operation_status": "unknown"
}
```

| Поле | Обязательно | Смысл |
|---|---|---|
| `error_code` | да | машинный код из каталога §3 |
| `message` | да | текст для пользователя, на русском, без внутренних деталей |
| `operation_id` | нет | если ошибка связана с операцией |
| `operation_status` | нет | состояние операции **после** ошибки |
| `details` | нет | машиночитаемые детали (например, `current_draft_version`) |

`Content-Type: application/json`. `trace_id` в тело не добавляется — он идёт
заголовком `X-Request-Id` и попадает только в логи (клиенту не нужен, а в
аналитику не должен попадать вовсе).

> Отличие от RFC 9457 (Problem Details), который использовался в первой версии
> документа: §10.3 ТЗ фиксирует плоские поля, поэтому `type`/`title`/`status` не
> используются. Это осознанное отклонение, зафиксированное в
> [спеке §15](../../specs/access-request.md).

## 2. Каталог кодов

| HTTP | `error_code` | Причина | Что меняется в состоянии |
|---|---|---|---|
| 400 | `VALIDATION_FAILED` | невалидные параметры, нет `Idempotency-Key` | ничего |
| 401 | `USER_NOT_FOUND` | неизвестный профиль `X-Test-User-Id` | не применимо |
| 403 | `RBAC_ACCESS_DENIED` | политика §11.3 вернула DENY | операция остаётся `awaiting_confirmation` |
| 404 | `OPERATION_NOT_FOUND` | операции нет или она чужая | не применимо |
| 409 | `DRAFT_VERSION_CONFLICT` | подтверждение по устаревшей версии черновика | `awaiting_confirmation` |
| 502 | `UPSTREAM_ERROR` | сервис ответил 5xx/невалидным телом | `failed` |
| 503 | `UPSTREAM_ERROR` | соединение не установлено (запрос не уходил) | `failed`, повтор безопасен |
| 504 | `UPSTREAM_TIMEOUT` | ответ не получен за таймаут | `unknown` |
| 500 | `INTERNAL_ERROR` | прочее | без изменений |

Коды — часть контракта: `ErrorCode` в
[`contracts/api.yaml`](../../contracts/api.yaml). Новый код добавляется в
контракт до реализации (AD-9).

## 3. Политика повторов

| Ситуация | Повтор разрешён | Что делает клиент |
|---|---|---|
| `failed` (502/503) | да, с новым `operation_id` | показывает ошибку и кнопку новой попытки |
| `unknown` (504) | нет | только `reconcile` |
| `RBAC_ACCESS_DENIED` | нет | объясняет ограничение, предлагает наставника |
| `DRAFT_VERSION_CONFLICT` | да, по актуальной версии | обновляет карточку |
| `OPERATION_NOT_FOUND` | нет | возвращается к контексту |
| 500 | да, вручную | сообщение + повтор действия |

Правило: клиент не решает, дошёл ли запрос. Различать «не дошло» и «неизвестно»
может только адаптер сервиса доступов по типу сбоя (соединение не установлено vs
таймаут ответа).

## 4. Что не попадает в ответ

Ключи, токены, SQL, стек-трейсы, содержимое закрытых документов
(`doc_03_lead_internal_policy`), `user_id` других пользователей. Диагностика —
в логах по `X-Request-Id`.

## 5. Ошибки LLM-контура

| Сбой | Ответ API | Пользователь видит |
|---|---|---|
| провайдер недоступен | 504 `UPSTREAM_TIMEOUT` | «не удалось получить ответ, повторите»; карточка не создаётся |
| провайдер вернул невалидный инструментальный вызов | операция не создаётся | уточняющий вопрос (FR-03) |
| нет доступа к документам для ответа | 200 + `sources: []` | честный отказ и кнопка наставника (AC-05) |

Ошибка LLM никогда не превращается в «успешно создано»: единственный источник
успеха — сохранённая заявка (FR-06, INV-02).
