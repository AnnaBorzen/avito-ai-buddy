## 1. Главная цель и рекомендуемый объём

Создать помощника, который помогает стажёру понять следующий шаг адаптации и довести выбранную организационную задачу до проверяемого результата, не заменяя наставника в содержательной работе.

MVP: один глубоко проработанный сценарий -запрос доступа в пространство своей команды. Это выбранная нами интерпретация задачи, а не обязательный сценарий организаторов. В предоставленном чек-листе запрос доступа к пространству команды/кластера относится к первой неделе; доступы к инструментам и каналам также присутствуют среди организационных шагов.

Пользователь и задача

Основной пользователь: синтетический backend-стажёр конкретной тестовой команды.

Ситуация: нужно изучить материалы команды, но нет доступа к её пространству.

Задача: понять порядок обращения, корректно подать запрос и видеть его статус и следующий шаг.

Гипотеза пользы: меньше рутинных уточнений наставнику и меньше времени на правильную подачу запроса.

Необоснованное обещание, которого избегаем: «помощник автоматически выдаёт все доступы».

Граница результата

Успех действия в MVP -сервис-имитация создал и сохранил корректную заявку, а интерфейс показывает её ID, фактический статус и дальнейшие действия.

Созданная заявка ≠ согласованная заявка ≠ выданный доступ. Если сервис вернул “ожидание”, помощник не сообщает, что доступ уже получен

Входит в MVP

Контекст тестового стажёра: роль, команда, этап выбранного сценария.

Ответы на вопросы о выбранной процедуре на основе доступных этому пользователю тестовых материалов.

Ссылка/указатель на использованный источник, явно помеченный как тестовая инструкция.

Уточнение недостающих параметров запроса.

Карточка предварительного просмотра и явное подтверждение отправки.

Вызов имитации корпоративного сервиса, сохранение и показ результата.

Этапы сценария, текущий статус и следующий шаг.

Обработка отсутствующих знаний, отказа в правах, таймаута, повторного нажатия и восстановления после обновления страницы.

Проверка прав, события аналитики, автоматизированные тесты, SDD и воспроизводимый запуск.

## 2. Путь пользователя

| Шаг | Действие пользователя | Поведение системы | Проверяемый результат |
|---|---|---|---|
| Понять задачу | Открывает помощника | Показывает контекст, этап и задачу | Пользователь видит, зачем нужен доступ |
| Разобраться | Спрашивает, как запросить доступ | Находит доступную тестовую инструкцию, отвечает в рамках неё | Есть понятный ответ и источник |
| Подготовить | Уточняет нужное пространство | Запрашивает только недостающие параметры | Черновик запроса валиден |
| Подтвердить | Проверяет и подтверждает карточку | Backend повторно проверяет права и параметры | Есть явное разрешение пользователя на действие |
| Отправить | Ожидает результат | Выполняет инструмент через адаптер сервиса | Сервис возвращает ID и статус |
| Продолжить | Смотрит результат | Сохраняет и показывает заявку; указывает следующий шаг | После обновления страницы заявка остаётся доступной |

Состояния

Разделить три разных сущности:

Шаг сценария (Step Status): not_started, in_progress, blocked, done.

Отправка операции (Operation Status): draft, awaiting_confirmation, submitting, succeeded, failed, unknown.

Статус заявки во внешнем сервисе (Ticket Status): pending, approved, rejected; для MVP достаточно реального поддерживаемого подмножества.

unknown означает, что запрос мог дойти до сервиса, но ответ потерян. Нельзя сразу создавать новую заявку: сначала проверить состояние исходной операции. Конкретный словарь статусов команда согласует до реализации.

## 3. Функциональные требования и приёмка

| ID | Требование | Критерий приёмки | Исполнитель |
|---|---|---|---|
| FR-01 | Контекст стажёра | Ответ и план учитывают тестовую команду и роль из серверного контекста | Backend + ML |
| FR-02 | Ответ по материалам | Помощник использует только доступные документы; показывает источник; не называет синтетику регламентом Авито | ML + Frontend |
| FR-03 | Недостаток информации | Задаёт уточнение либо честно сообщает отсутствие ответа и предлагает обращение к человеку | ML |
| FR-04 | Предпросмотр операции | Пользователь видит ресурс, получателя/маршрут обращения и параметры до отправки | Frontend + Backend |
| FR-05 | Подтверждение | До явного подтверждения изменяющий состояние инструмент не выполняется | Backend + ML |
| FR-06 | Создание заявки | Имитация сервиса сохраняет заявку и возвращает ID и статус | Backend |
| FR-07 | Показ и сохранение результата | UI показывает данные ответа сервиса; повторное открытие получает ту же заявку с backend | Backend + Frontend |
| FR-08 | Прогресс и следующий шаг | Отправка запроса отражена в этапах; ожидание согласования не выглядит как выданный доступ | Product + Frontend |
| FR-09 | Права | Пользователь не читает чужую заявку и не вызывает недоступную операцию даже при прямом обращении к API | Backend |
| FR-10 | Повторные запросы | Двойное нажатие и безопасный повтор не создают дубликат одной операции | Backend + Frontend |
| FR-11 | Сбой интеграции | Нет ложного сообщения об успехе; понятный статус и безопасный путь восстановления | Backend + Frontend |
| FR-12 | Отзывчивость | Локальные действия соответствуют ориентиру PDF менее 1 с; ожидание LLM/сервиса не блокирует UI | Frontend |

Примеры проверок Given / When / Then

AC-01 -успешная подача: Дано: разрешённое пространство, валидные параметры, доступный тестовый сервис. Когда стажёр подтверждает отправку. Тогда сохраняется одна заявка, UI показывает её ID и pending, а следующий шаг объясняет ожидание согласования.

AC-02 -запрет действия: Дано: у пользователя нет права запрашивать выбранный ресурс. Когда он просит помощника обойти запрет либо вызывает API напрямую. Тогда backend отказывает, сервис не создаёт заявку, закрытые сведения не попадают в ответ.

AC-03 -повторное нажатие: Дано: отправка одной операции уже началась. Когда пользователь нажимает повторно или повторяет запрос после сетевого сбоя. Тогда механизм идемпотентности не создаёт вторую заявку.

AC-04 -потерянный ответ сервиса: Дано: сервис мог сохранить заявку, но ответ не дошёл. Когда возникает таймаут. Тогда система не утверждает ни успех, ни окончательную неудачу, проверяет состояние исходной операции и не выполняет слепой повтор.

AC-05 -нет источника: Дано: в доступных материалах нет нужного правила. Когда стажёр спрашивает об этом. Тогда помощник не сочиняет порядок действий, обозначает ограничение и предлагает безопасный следующий шаг.

AC-06 -сохранённость: Дано: заявка создана. Когда пользователь обновляет страницу. Тогда результат снова загружается с backend, а не существует только в сообщении чата.

## 4. Минимальный интерфейс

Один рабочий экран, а не набор отдельных кабинетов:

Контекст тестового пользователя и команды (с переключателем профиля в шапке для демонстрации жюри).

Этапы выбранного сценария и текущая задача.

Чат с источниками ответа (явные бейджи [Тестовая инструкция]).

Карточка действия: параметры → подтверждение → ожидание → результат.

Номер/статус заявки и следующий шаг.

Кнопка/ссылка обращения к наставнику при необходимости.

Обязательные для проектирования состояния: первоначальная загрузка, пустой диалог, ответ, уточнение, нет данных, нет прав, подтверждение, ожидание модели, ожидание сервиса, ошибка, неопределённый результат операции (unknown), успешная подача.

## 5. SDD: спецификации поведения AI и инструментов

Предлагаемая структура репозитория

```text
docs/PRD.md                 -цель, аудитория, scope, путь, критерии приёмки
docs/metrics.md             -определения метрик, события, план проверки
specs/access-request.md     -поведение AI, состояния, ограничения, негативные случаи (SDD)
contracts/api.yaml          -согласованный формат запросов/ответов/ошибок (OpenAPI)
evals/                      -синтетические задания, эталоны, результаты прогонов
README.md                   -инструкция запуска (Docker), тестовые данные и отчёт покрытия
```

Правила для SDD

Идентичность, команда и разрешения поступают из доверенного серверного контекста. Текст «я руководитель» в чате их не меняет.

Поиск использует разрешённый набор документов до передачи контекста в LLM.

Документы считаются источниками данных, а не инструкциями, способными изменить правила агента (защита от Prompt Injection).

Неизвестные поля уточняются; обязательные параметры не выдумываются.

Изменяющая состояние операция требует подтверждения пользователя. Подтверждение связано с конкретной версией черновика; после изменения ресурса или других значимых полей нужно новое подтверждение.

Backend проверяет доступ и валидирует параметры независимо от поведения LLM.

Успех сообщается только по подтверждённому результату инструмента, который сохранён системой.

Статус pending не превращается в текст «доступ выдан».

Ошибки, повтор и неопределённый исход определены явно.

Секреты, чужие данные и закрытые документы не выводятся в UI и обычную продуктовую аналитику.

## 6. Метрики и аналитика

Бизнес-результат для пилота: снижение минут рутинной помощи наставника на стажёра за сопоставимый период без ухудшения успешности адаптации. Основная операционная метрика MVP: доля корректно поданных запросов без рутинной помощи. Она проверяет выбранный сценарий, но сама по себе ещё не доказывает экономию времени наставника.

По ориентировочной оценке Авито, занятость наставника составляет 40–48 часов за 6-месячную программу и 55–65 часов за 9-месячную (включая 1:1, ревью компетенций, обучение, обратную связь и встречи). Эти часы нельзя целиком объявлять потенциальной экономией AI-buddy. Оценивать нужно только реально изменяемую рутину с учётом исправления ошибок и поддержки системы.

Предлагаемая единица анализа: одна задача подачи запроса (task_instance_id), а не сообщение чата. Повторы одной операции не увеличивают число задач или успехов. Предлагаемое окно для пилота: 24 часа с начала задачи.

| Метрика | Определение | Источник / ответственность |
|---|---|---|
| Основная: доля корректно поданных запросов без рутинной помощи | Число начатых задач, где в окне создана и проверена корректная заявка без помощи наставника при подготовке / все подходящие начатые задачи с закрытым окном | Backend: результат сервиса; Product: проверка корректности |
| Время до корректной подачи | Время от старта задачи до подтверждённого сохранения корректной заявки; медиана, число наблюдений и доля незавершённых рядом | События backend; Product/DS: расчёт |
| Рутинная нагрузка наставника | Минуты на повторяющиеся организационные объяснения и исправление ошибочных заявок на стажёра за сопоставимый период | Короткий дневник/разметка наставника; не только клики в чате |
| Повторное обращение по той же задаче | Доля завершённых задач, потребовавших исправления или повторной помощи в выбранном окне наблюдения | Связанные события + опрос/дневник; зрелые окна |
| Качество ответа (RAG Faithfulness) | Доля проверенных ответов, где утверждения подтверждаются доступными источниками и соответствуют контексту роли/команды | Размеченный eval-набор, проверка Product + ML |
| Корректность действия (Tool Accuracy) | Доля проверок, где выбран нужный инструмент, параметры и права верны, а результат правильно отображён | Eval и интеграционные тесты |
| Инженерные ограничения | Покрытие строк прикладного кода >80%; ориентир локального UI <1 с; отдельно задержки модели/сервиса и ошибки | Воспроизводимые отчёты тестов и измерения |

Минимальный tracking plan

| Событие | Где фиксируется | Условие |
|---|---|---|
| task_started | Backend | Создан экземпляр выбранной задачи |
| answer_delivered | Backend | Ответ доставлен; есть метаданные источников без закрытого содержимого |
| action_proposed | Backend | Создан валидный черновик действия |
| action_confirmed | Backend | Получено подтверждение пользователя |
| action_succeeded | Backend | Получен и сохранён подтверждённый результат сервиса |
| action_failed | Backend | Подтверждена неудача операции |
| action_status_unknown | Backend | Нужна сверка результата после неопределённого исхода |
| handoff_requested | Backend | Пользователь запросил помощь человека |
| task_feedback_submitted | Backend | Получена оценка решения задачи |

Общие поля событий: event_id, время UTC, синтетический/псевдонимный идентификатор пользователя, task_instance_id, scenario_id, operation_id при наличии, версия сценария/модели, результат, категория ошибки, длительность, признак тестового режима. Не записывать ключи, чувствительные сведения и полный текст разговоров в обычную аналитику.

## 8. Спецификация AI-инструментов (Function Calling / MCP)

Инструменты разделены на два контура: AI-агент может только проверять доступность и формировать безопасный черновик (propose_access_request), но НЕ может самостоятельно вызвать отправку заявки в корпоративный сервис без подтверждения пользователем на фронтенде (FR-05).

## 8.1. Инструмент формирования черновика: propose_access_request

Вызывается LLM-агентом, когда пользователь выразил намерение получить доступ и предоставил все обязательные параметры. Если параметр не указан (например, не назван access_level или justification), агент обязан задать уточняющий вопрос в чате и НЕ вызывать инструмент с выдуманными значениями.

```text
{
  "name": "propose_access_request",
  "description": "Создаёт черновик (draft) заявки на доступ к корпоративному ресурсу для предпросмотра и подтверждения стажёром. Не выполняет реальную отправку в сервис.",
  "parameters": {
    "type": "object",
    "properties": {
      "resource_id": {
        "type": "string",
        "enum": [
          "space_auto_backend_wiki",
          "repo_auto_core_sandbox",
          "space_goods_search_wiki",
          "db_fintech_prod_cluster"
        ],
        "description": "Точный идентификатор ресурса из каталога."
      },
      "access_level": {
        "type": "string",
        "enum": ["read", "write"],
        "description": "Запрашиваемый уровень доступа (read -чтение, write -редактирование). Должен быть явно назван пользователем."
      },
      "justification": {
        "type": "string",
        "minLength": 10,
        "maxLength": 300,
        "description": "Деловое обоснование запроса со слов пользователя (зачем нужен доступ)."
      }
    },
    "required": ["resource_id", "access_level", "justification"],
    "additionalProperties": false
  }
}
```

Важное архитектурное правило: Поля user_id, team_id и approver_id намеренно исключены из параметров LLM. Backend подставляет их строго из серверной сессии и справочника команды, чтобы исключить подмену через промпт-инъекцию.

## 9. База знаний для RAG (Синтетические инструкции).

Документ 1: doc_01_onboarding_access.md (Доступен всем стажёрам)

```text
---
doc_id: "doc_01_onboarding_access"
title: "[ТЕСТОВАЯ ИНСТРУКЦИЯ] Порядок запроса доступов на первой неделе стажировки"
allowed_roles: ["intern", "mentor", "lead"]
allowed_teams: ["*"]
is_synthetic: true
---
ВНИМАНИЕ: Это синтетическая тестовая инструкция для прототипа хакатона (не является регламентом Авито).
1. Зачем нужен доступ на первой неделе:
На первой неделе адаптации backend-стажёру необходимо изучить архитектуру сервисов и командные соглашения. Для этого требуется оформить доступ к пространству базы знаний своей команды (например, для команды Auto Backend -ресурс `space_auto_backend_wiki`) и учебному репозиторию-песочнице (`repo_auto_core_sandbox`).
2. Какие параметры нужны для подачи заявки:
Для создания заявки через AI-buddy стажёр должен указать три обязательных параметра:
- Идентификатор или название ресурса (например, пространство документации команды `space_auto_backend_wiki`);
- Уровень прав: `read` (только чтение материалов) или `write` (создание заметок и отчётов по онбордингу);
- Обоснование (justification): краткая причина запроса (например, «Прохождение чек-листа первой недели, изучение документации команды»).
3. Как происходит согласование и что делать после отправки:
- После подтверждения карточки в интерфейсе создаётся заявка в сервисе доступов со статусом `pending` (ожидает согласования).
- Создание заявки НЕ означает мгновенную выдачу доступа. Заявку рассматривает руководитель команды (Team Lead), который назначается системой автоматически.
- Стандартный срок рассмотрения заявки руководителем -до 4 рабочих часов. Пока заявка в статусе `pending`, стажёр может перейти к изучению открытого справочника AvitoTech Playbook или подготовить вопросы к первой встрече 1:1 с наставником.
```

## 11. Definition of Done и план тестирования (>80% coverage)

Функция считается готовой, если:

☐ соответствует согласованной спецификации и критериям приёмки (AC-01..AC-06);

☐ работает в общей Docker-сборке, а не только локально у автора;

☐ интегрирована с реальными компонентами прототипа;

☐ имеет позитивные и применимые негативные автотесты;

☐ не нарушает права доступа (RBAC) и сохраняет требуемый результат в БД;

☐ показывает необходимые UI-состояния, если затрагивает интерфейс;

☐ отправляет согласованные события аналитики без секретов и лишних данных;

☐ изменение отражено в документации (README / SDD) и принято другим участником.

Контроль покрытия >80%: Покрытие >80% относится к написанному командой прикладному коду, а не только к backend. Исключаются зависимости, сгенерированный код и сами тесты (PDF кейса, стр. 12). Если отчёты раздельные по языкам (Backend + ML + Frontend), в README и отчёте прикладываются покрытые и исполняемые строки по каждому модулю; нельзя получать общий показатель простым средним процентов компонентов.
